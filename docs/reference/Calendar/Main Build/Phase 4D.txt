## Part 1 – Organizer booking edit / reschedule

Implement the organizer-side ability to edit or reschedule an existing booking.

Recommended routes under the existing organizer namespace:
- `GET /events/:eventId/calendar/bookings/:bookingId/edit`
- `POST /events/:eventId/calendar/bookings/:bookingId`

Use `calendar.edit.bookings` permission protection.

Requirements:
- Allow organizer to update:
  - selected date(s)
  - selected item(s)
  - selected occurrence(s) in timed mode
  - notes
  - relevant registrant fields if appropriate
- Reuse the booking validation logic as much as possible rather than duplicating rules.
- Enforce the same rules as initial booking:
  - date window
  - blocked dates
  - capacity
  - overlap constraints
- Be conservative:
  - if the edited selection conflicts, reject with clear error messages
  - do not partially save invalid booking changes
- Preserve historical clarity in booking selections/snapshots.
- Canceled bookings should not be editable unless you decide on a clear safe rule; default to non-editable if uncertain.

Views:
- booking edit form
- reuse existing styling patterns
- make it understandable on mobile, even if not heavily polished

Tests:
- happy-path reschedule
- attempt to move into blocked/full/unavailable slot
- permission enforcement
- canceled-booking behavior

- Include:
  - booking summary
  - confirmation page link
  - optionally the ICS link
- Use environment/config-based mail setup
- If the repo does not yet have a mail provider, choose a minimal abstraction that keeps the app clean:
  - e.g. `src/services/mailService.js`

Important:

- Use env vars
- If actual provider delivery cannot be tested in CI, structure it so tests can stub/mock it cleanly

Tests:
- service-level tests for “should send / should not send”
