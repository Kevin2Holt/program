Public:

Organizer:

## Calendar core entities
- `CalendarConfig`
- `CalendarItem`
- `CalendarOccurrence`
- `CalendarBooking`
- `CalendarBookingSelection`
- `CalendarAvailabilityRule`
- `CalendarAvailabilityRuleTarget`

## Calendar core data rules
- One booking parent can have many booking selections.
- Date-only mode does not require occurrence rows.
- Timed mode uses real occurrence rows.
- Availability rules remain rules, not generated blackout occurrences.
- Items and occurrences with history should be archived/deactivated, not hard deleted.
- Booking selections preserve simple historical snapshot fields.
- Minimal booking status model for now: `active` and `canceled`.

## Pending selection state
- Use **server session-backed pending selection state**.
- It is temporary interaction state only, not the source of truth for final booking success.

## Submission safety
- Final submission must revalidate availability transactionally.
- Use redirect-after-post.
- Include anti-double-submit protection via a submission token or equivalent dedupe mechanism.

## Confirmation reference
- Confirmation refs must be opaque, non-sequential, scoped to one booking, safe for public viewing by possession of link, and not usable as edit links.

## Time zone
- Use one **canonical event time zone** for this side project’s scheduling logic, occurrence display, booking validation, overlap logic, confirmation behavior, and add-to-calendar behavior.

## Email confirmation dependency
- Email confirmation cannot be enabled unless email collection is enabled.
- The organizer UI control should remain visible but disabled/grayed out when unavailable.

## Permissions
Use the `calendar.*` namespace and keep it shallow:
- `calendar.view`
- `calendar.view.details`
- `calendar.edit`
- `calendar.edit.items`
- `calendar.edit.availability`
- `calendar.edit.bookings`
- `calendar.export`

Even if current practical access is simplified early on, code explicit permission checks and permission scaffolding so later role-aware enforcement is clean.
