# Scope for Phase 4B.1

Implement only the organizer setup and calendar configuration layer.

## In scope

### 1. Organizer setup page
Implement the organizer setup page at:

- `/events/:eventId/calendar/setup`

This page should be a real server-rendered configuration form, not a placeholder.

It should load the existing calendar config for the event if present, or provide sensible defaults for a not-yet-configured event.

### 2. Event-level calendar config persistence
Implement persistence for the event-level calendar configuration described in the specifications.

At minimum, support editing and saving:

- calendar enabled/disabled
- public visibility state
- public title / label if supported by schema
- date window mode
- fixed date range fields where relevant
- rolling window fields where relevant
- rolling window unit behavior
- time behavior mode
- canonical event time zone
- structured public form configuration
- notes enabled
- email confirmation enabled
- add-to-calendar enabled
- calendar export mode default
- any bounded config fields already planned in Phase 3 and supported by Phase 4A schema

Use the existing schema and services where possible. If a small migration adjustment is truly necessary, make the minimum safe change and explain why.

### 3. Validation
Implement server-side validation for the setup form.

Validation should cover at minimum:
- required fields
- invalid enum values
- valid fixed date ranges
- valid rolling window configuration
- canonical time zone presence/format if the app expects a bounded list or string
- email confirmation cannot be enabled unless email collection is enabled
- structured form config must remain within the bounded supported field system
- no acceptance of arbitrary freeform form-builder config

If client-side enhancement is added, it must be optional and must not replace server validation.

### 4. Structured public form config UI
Implement the organizer UI for the bounded field system.

The setup form should support the structured configuration model already decided, rather than a freeform builder.

At minimum, support organizer control over the enabled/required state of the predefined public fields relevant to the current specifications, including:
- name
- phone number
- email if supported in the Phase 2/3 spec and schema
- notes toggle as separately controlled behavior if that is modeled separately

Also include the phone metadata assumptions already established:
- preferred contact method: call / text
- number type: cell / WhatsApp

Do not invent a drag-and-drop custom form system.

### 5. Email confirmation dependency behavior
Implement the rule that email confirmation cannot be enabled unless email collection is enabled.

The UI should:
- show the email confirmation control
- disable or gray it out when unavailable
- preserve clear explanatory text

The server must enforce the same rule regardless of UI state.

### 6. Setup page UX
Keep the page clean, server-rendered, and aligned with the existing app style.

Use progressive disclosure where appropriate so the form does not feel overwhelming.

A good approach would be grouped sections such as:
- Calendar visibility
- Date window
- Time behavior
- Public signup fields
- Confirmation and export preferences

Do not overdesign this page, but it should feel intentional and integrated.

### 7. Organizer calendar landing page integration
Update the organizer calendar landing page as needed so it meaningfully links to or summarizes setup state.

At minimum, it should no longer feel disconnected from the setup flow.

### 8. Tests
Add focused tests for this milestone.

At minimum, cover:
- GET setup page
- POST/PATCH save behavior
- valid config persistence
- invalid config rejection
- email confirmation dependency enforcement
- fixed vs rolling window validation
- permission protection for organizer setup route

Use the existing test framework and project conventions.
