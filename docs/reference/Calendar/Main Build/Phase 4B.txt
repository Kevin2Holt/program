### 2.1 – Item management (organizer)

Goal: allow organizers to manage `CalendarItem` records for an event:

- list items
- create item
- edit item
- archive/deactivate item (no hard delete where bookings might exist)

Use the existing schema, models, services, and routes from Phase 4A as your base.

Implement:

1. **Organizer routes and controllers**
   - Organizer-facing routes under the existing calendar organizer family, e.g.:
     - `GET /events/:eventId/calendar/items`
     - `GET /events/:eventId/calendar/items/new`
     - `POST /events/:eventId/calendar/items`
     - `GET /events/:eventId/calendar/items/:itemId/edit`
     - `POST /events/:eventId/calendar/items/:itemId` (or PATCH, but if you choose PATCH ensure HTML form support or method override is handled)
     - `POST /events/:eventId/calendar/items/:itemId/archive` (or similar) for archive/deactivate.
   - Guard all routes with the appropriate `calendar.edit.items` (or equivalent) permission via the existing permission middleware.

2. **Validation**
   - Required: name.
   - Capacity: positive integers only (allow 1 for missionary use case, but design for higher).
   - Color/shape: validate within supported palette/shape set if you have enums; otherwise, ensure sanitized/normalized input.
   - Status: enforce valid status values (active/archived/etc. as per schema).

3. **Views**
   - Organizer item list page:
     - Show items for the event.
     - Show status (active vs archived).
     - Provide links to edit/archive.
   - Item create/edit form:
     - Fields for name, capacity, color, shape, status (if applicable).
     - Use same layout and CSS patterns as the setup page.
     - Show validation errors.

4. **Archival behavior**
   - Do not hard delete items that may have bookings or selections.
   - Ensure archived items:
     - are excluded from future public availability,
     - but remain usable for historical booking display.

Add tests for:
- basic item CRUD (within what’s reasonable),
- permission enforcement,
- validation enforcement (e.g., capacity <= 0 is rejected).

### 2.2 – Occurrence management (timed offerings)

Goal: allow organizers to define `CalendarOccurrence` rows for timed offerings when the calendar is in a “timed” mode.

Use the Phase 3 plan as your guide:

- Date-only mode: no occurrences required.
- Timed mode: each timed offering is an occurrence row.

Implement:

1. **Organizer routes and controllers**
   - Under the existing calendar organizer namespace:
     - `GET /events/:eventId/calendar/occurrences`
     - `GET /events/:eventId/calendar/occurrences/new`
     - `POST /events/:eventId/calendar/occurrences`
     - `GET /events/:eventId/calendar/occurrences/:occurrenceId/edit`
     - `POST /events/:eventId/calendar/occurrences/:occurrenceId`
     - `POST /events/:eventId/calendar/occurrences/:occurrenceId/archive` (or deactivate)
   - Guard with appropriate `calendar.edit` or `calendar.edit.items`/`calendar.edit.availability` depending how you split it (stay consistent with your existing permission surface).

2. **Fields/validation**
   - Associate each occurrence with:
     - an `item_id`
     - a `service_date`
     - `start_time` and either `end_time` or `duration_minutes`
   - Validation:
     - service_date must be valid, within the configured date window, and not obviously malformed.
     - start_time and end_time/duration must define a positive-time range.
     - respect the canonical event time zone (no need for full DST complexity; just treat times as in that zone).
   - Optionally support occurrence-level capacity overrides (if schema supports), with validation to ensure positive integers.

3. **Overlap behavior (organizer-side)**
   - For this phase, implement basic overlap checks on save when time overlap prevention is enabled:
     - If the Phase 3/Phase 4A services already include overlap math helpers, reuse them.
     - Ensure you don’t silently save overlapping occurrences that should be prevented.
   - If there is ambiguity, implement a conservative rule (e.g., prevent overlapping occurrences for the same item by default) and document it in a comment.

4. **Views**
   - Occurrence list:
     - Group by item where practical.
     - Show date, start/end time, capacity override if any, status.
   - New/edit form:
     - Use the same layout theming.
     - Provide item dropdown, date, start time, end time/duration.

Add tests for:
- valid occurrence creation,
- invalid times/dates rejection,
- overlap prevention in the cases you implement,
- permission protection.

### 2.3 – Availability rules (recurring + one-time)

Goal: allow organizers to define `CalendarAvailabilityRule` entries that block selection on certain dates/repetition patterns, consistent with Phase 2/3.

Implement:

1. **Organizer routes and controllers**
   - Under the calendar organizer family:
     - `GET /events/:eventId/calendar/availability`
     - `GET /events/:eventId/calendar/availability/new`
     - `POST /events/:eventId/calendar/availability`
     - `GET /events/:eventId/calendar/availability/:ruleId/edit`
     - `POST /events/:eventId/calendar/availability/:ruleId`
     - `POST /events/:eventId/calendar/availability/:ruleId/archive` (or deactivate)
   - Guard with `calendar.edit.availability`.

2. **Rule types and scopes**
   Implement at least:
   - **One-time rules:**
     - Single date.
     - Apply to all items, a single item, or a selected subset via the rule-target join table.
   - **Recurring rules:**
     - Weekly by weekday (with one or more weekdays).
     - Optional: monthly by specific day-of-month or by weekday pattern (e.g., first Monday).
   - Scope:
     - all items.
     - selected items via `CalendarAvailabilityRuleTarget`.

The specific recurrence encoding should align with fields and patterns outlined in Phase 3 and the existing schema.

3. **Validation**
   - Validate rule type (one-time vs recurring).
   - Validate date values and recurrence parameters.
   - Ensure at least one target (all items or specific item IDs).
   - Ensure rules are scoped to the correct `calendar_config_id`.

4. **Integration with existing availability service**
   - Wire the new CRUD UI and controllers to the existing `calendarAvailabilityService` (created in Phase 4A) so:
     - organizer-created rules are visible in the service’s resolution,
     - future public browsing logic can reuse the same resolution API.

5. **Views**
   - Availability list:
     - Show rules grouped by type (one-time vs recurring).
     - Show which items they target and whether they’re active.
   - Form:
     - Simple grouped inputs for rule type, date(s), recurrence, and item scope.

Add tests for:
- creating valid one-time and recurring rules,
- invalid combinations (e.g., missing recurrence parameters),
- rule-target behavior (all vs selected items),
- rules being picked up by the availability service as expected.
