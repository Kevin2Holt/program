- Templating engine: EJS

- No SPA

Important architecture expectations:
- Public event access is code-first and route-based.
- The main public route model uses event codes in the URL path.
- Organizer pages are authenticated server-rendered pages.
- The codebase follows a layered architecture:
  - routes
  - controllers
  - services
  - models
  - views [file:2][file:159]

Key repo/architecture guidance from CLAUDE.md:
- Models are thin and pg-backed.
- Services own validation and product rules.
- Controllers orchestrate request handling and rendering.
- Routes declare URL mapping and middleware, but should not own business logic.
- Views render only.
- Client-side JS is optional progressive enhancement and must not become the source of truth. [file:159]

9. CORE CALENDAR PRODUCT CONCEPT
==================================================

The core abstraction is an Item.

Definition of Item:
- An Item is the thing a public user signs up for on a date or occurrence.
- Examples:
  - missionary companionship
  - meal-train need
  - breakout session
  - seminar
  - RSVP target [file:3][file:5]

Each Item can have:
- name
- capacity
- color
- shape
- availability/unavailability rules
- active/archive status
- time-related behavior where applicable [file:3][file:5]

Capacity meaning:
- Capacity is how many signups the Item can accept for a given date or occurrence.
- In date-only mode, capacity applies per item per date.
- In time-enabled mode, capacity applies per occurrence.
- Timeslot mode should behave like occurrence mode. [file:3][file:5]

11. LOCKED CALENDAR PRODUCT DECISIONS FROM PHASE 1 / PHASE 2
==================================================

11.1 Number of Items
- The system must support any number of Items.
- Do not hardcode the missionary count of 4. [file:3]

11.2 Item names
- Item names are organizer-defined.
- Do not hardcode names. [file:3]

11.3 Item visual identity
Each Item has:
- one identifying color
- one identifying shape

Rules:
- colors/shapes can be auto-assigned by default
- organizers can change them
- colors must be distinguishable and visible in both dark and light mode
- outlines/borders may be used for visibility
- shapes should be simple and recognizable
- supported shapes include:
  - capital letters A-Z
  - numbers 0-9
  - basic shapes such as circle, square, triangle [file:3]

11.4 Date window model
Organizers can choose:
- fixed date range
- ongoing rolling window

Ongoing rolling window rules:
- organizer chooses how far into the future signups are allowed
- organizer chooses window size using days, weeks, or months
- if using weeks or months, the window snaps to natural boundaries rather than raw day counts [file:3]

11.5 Multiple Item selection
- Public users can select multiple Items for a single day.
- Public users can also select across multiple days in one flow. [file:3][file:5]

11.6 Time behavior
- Time support is optional.
- If enabled, use specific timeslots / occurrences, not freeform user-entered times.
- Time-enabled mode must support:
  - fixed time occurrences
  - selectable timeslots
  - repeated same-day occurrences
  - overlap prevention where relevant [file:3][file:5]

11.7 Double booking / capacity
- In the missionary use case, no double-booking for the same Item on the same day.
- More generally, capacity governs availability.
- The same Item cannot be selected twice on the same date in date-only mode by default.
- Same Item on different dates is allowed. [file:3][file:5]

11.8 Public form fields
For the missionary baseline:
- name
- phone number

Phone should support metadata:
- preferred contact method: call / text
- number type: cell / WhatsApp [file:3][file:5]

11.9 Notes
- Free-form notes are allowed only if the organizer enables them. [file:3][file:5]

11.10 Validation / friction
- Organizer-configurable where appropriate within the structured field system.
- Do not turn the module into a freeform form builder. [file:3][file:5]

11.11 Confirmation behavior
- A confirmation page is always required.
- Email confirmation is optional.
- An add-to-calendar action may be shown on the confirmation page.
- Calendar export mode can be:
  - single combined event (default)
  - separate event per selected Item [file:3][file:5]

11.12 Organizer visibility
- Organizers should be able to see the full list of signups and associated details. [file:3]

11.13 Availability visibility
Public users should only see:
- available
- unavailable

Organizers should be able to see detailed statuses:
- available
- full
- blocked [file:3][file:5]

11.14 Recurring unavailability
Should support at least:
- daily
- weekly with selected weekdays
- bi-weekly
- monthly by date
- monthly by weekday pattern

Custom interval support is optional and not required initially. [file:3][file:5]

11.15 One-time unavailability
- Must support blocking:
  - one Item
  - selected Items
  - all Items
- Initial implementation should use date-level one-time blocking.
- Occurrence-level one-time blocking can be a later enhancement. [file:3][file:5]

11.16 Structured form system
- Use a structured form system, not a freeform builder.
- Organizers choose from supported fields and required/optional states. [file:3][file:5]

17. CALENDAR PUBLIC EXPERIENCE
==================================================

Public experience goals:
- simple
- mobile-usable
- fast to scan
- event-integrated
- availability-focused [file:3][file:5]

What the public calendar should show:
- visible dates in the active date window
- one indicator per Item per date
- available vs unavailable state only
- time choices only when relevant
- current selection summary/cart
- the structured signup form at submission stage [file:3]

Indicator behavior:
- one indicator per Item, not one per remaining seat
- if Item has remaining capacity and is not blocked, show available
- if full or blocked, show unavailable (faded/disabled/grayed out)
- public should not see blocked vs full distinctions [file:3][file:5]

Filtering:
- item filters are allowed and helpful
- filters should be optional, not required for basic use
- hiding a selected Item via a filter should not clear that selection
- selected items remain in the pending summary unless invalidated by state changes [file:3][file:5]

Selection behavior:
- multiple Items on the same day: allowed
- multiple days in one flow: allowed
- same Item on different days: allowed
- same Item twice on same date in date-only mode: not allowed by default [file:3][file:5]

Time behavior:
- date-only mode: selecting an Item on a date creates a date-only selection
- fixed occurrence mode: user selects the occurrence directly
- timeslot mode: user selects the Item/date and then chooses from available timeslots
- repeated offerings on one day remain under one Item identity, not separate Items [file:3][file:5]

Overlap prevention:
- if enabled by the scheduling model, overlapping timed selections on the same day should be blocked
- the UI may prevent obviously invalid choices early, but final authority is server-side validation [file:3][file:5]

Submission flow:
1. browse/select Items/dates/occurrences
2. review current selections
3. fill structured form fields
4. submit
5. receive confirmation page [file:3]

Final submission rule:
- availability must be revalidated at final submission to prevent stale availability bugs and double-booking. [file:3][file:5]

Confirmation page:
- always required
- shows booked selections
- shows submitted identifying details as appropriate
- indicates whether email confirmation was sent
- may show add-to-calendar option if enabled [file:3][file:5]

Add-to-calendar behavior:
- organizer chooses:
  - single combined event (default)
  - separate event per selected Item/occurrence [file:3][file:5]

==================================================
19. AVAILABILITY AND BOOKING RULES
==================================================

An Item is available only if:
1. the date is inside the active date window
2. the Item is active
3. it is not blocked by one-time or recurring rules
4. capacity remains
5. overlap rules are not violated for the user where relevant [file:3][file:5]

Public unavailable if:
- blocked
- full
- outside date window
- occurrence no longer exists or is not offered [file:3]

Required precedence:
1. date window boundary
2. item active/archive status
3. one-time and recurring block rules
4. remaining capacity [file:5][file:159]

One-time vs recurring precedence:
- one-time rules should take precedence over recurring rules when both apply on the same date. [file:3][file:5]

Capacity source of truth:
- computed from persisted booking selections
- not from cached UI state [file:5]

Conflict handling:
- public conflict should fail clearly
- preserve unaffected valid selections where possible
- organizer edit conflict should be blocked and explained
- no silent overbooking in initial implementation [file:5]

20. TIME / OCCURRENCE RULES
==================================================

Unified occurrence model:
- timed bookable units should be modeled as occurrences, even when the UI refers to “timeslots.” [file:5]

Mode mapping:
- date-only item -> selected date only
- fixed time offering -> explicit occurrence row
- timeslot offering -> explicit occurrence row
- repeated same-day offering -> multiple occurrence rows under the same Item [file:5]

Required timing rules:
- duration should be required whenever overlap prevention depends on time ranges
- overlap logic compares same-day time ranges
- repeated offerings stay grouped under one Item identity
- date-only Items do not participate in overlap logic [file:5]

Time zone rule:
- use a single canonical event time zone
- use that time zone for:
  - display
  - overlap detection
  - booking validation
  - confirmation output
  - add-to-calendar output [file:5]
